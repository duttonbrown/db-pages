The MRP We Should Build (Not Buy)

A capability-by-capability study of MRPeasy and Katana, mapped against what we already have — and a phased plan for the pieces worth building ourselves. June 2026.

← The MRPeasy Decision

The framing

We don't need an MRP. We need four capabilities an MRP happens to bundle.

I studied both MRPeasy and Katana module by module. An MRP is really a dozen modules wired into one recalculation engine: BOM, inventory, procurement, production planning, scheduling, MRP run, costing, CRM/sales, shop floor, reporting. We've already built the production-specific half (BOM, wash list, travelers, consoles). Looking at everything the two vendors do, only four capabilities are both genuinely missing and genuinely worth having: inventory on-hand, low-stock alerts, a real PO system, and an all-parts demand view. The rest is either already built, irrelevant to a made-to-order shop, or not worth the complexity.

Your instinct on a PO system was right — and it's the keystone. It's the natural home for inventory tracking, it's the one thing we currently pay Katana ~$299+/mo for and barely use, and building it lets us cancel Katana.

The build — three phases, in priority order

Phase 1 delivers the alerts you asked for. Phase 2 builds the PO system and lets us cancel Katana. Phase 3 makes it all self-maintaining and adds the predictive layer. Each phase ships value on its own — you can stop after any one.

Phase 1 — Inventory levels & low-stock alerts

Do now · ~2–3 days
Reuses: Parts DB, n8n, Teams, Purchase Request Log. New cost: $0.
Goal: Know what's on hand, get pinged before anything runs out. This is the literal ask — "monitor inventory alert levels."
  1. Add two number properties to the Parts DB: Qty on Hand and Reorder Point. (There's already a stubbed-but-empty Inventory Transactions relation — the intent was always there.)
  2. Seed Reorder Point from a rule using inputs we already have: (annual use ÷ 52) × lead-time-weeks × safety factor. The 2025 Use and Lead Time fields are populated enough to do this for the parts that matter.
  3. Seed Qty on Hand from a one-time physical count of the ~80 high-velocity / long-lead parts — not all 455. Long tail can stay blank and be added as it's touched.
  4. Build one scheduled n8n workflow: nightly, read every part where Qty on Hand ≤ Reorder Point → post one Adaptive Card to the Operations Teams channel (part, on-hand, reorder point, vendor, lead time) with an "Add to purchase queue" button that drops a row into the Purchase Request Log.
✓ Delivers working low-stock alerts, end to end. After Phase 1 you have the thing you asked for.

Phase 2 — Real Purchase Order system (cancels Katana)

Do next · ~1–1.5 weeks
Reuses: Purchase Request Log (~30% there), Companies DB, the purchase console + worker already on the hub. New cost: $0 — and saves ~$299+/mo by killing Katana.
Goal: Turn the per-line request log into a real vendor-grouped PO system — the one Katana function we actually use — so we can cancel Katana.
  1. New Purchase Orders DB as a PO header: auto PO #, real relation to a vendor (Companies), status (Draft → Sent → Partially Received → Closed), order date, expected date, total.
  2. Add a real Vendor relation (to Companies) on every Purchase Request Log row — today vendor is a free-text string, which blocks all vendor-level grouping. Link each PRL line to its parent PO.
  3. Enrich the Companies/vendor master with the purchasing metadata it's missing: Payment Terms, Min Order Value, Account #, Contact Email, numeric Lead Time (days).
  4. Build a "What to reorder, grouped by vendor" view: every part at/under reorder point, bucketed by vendor, one-click → consolidated PO (Katana's exact "add other missing items from the same supplier" move).
  5. Generate a PO PDF to email the vendor (we already render traveler PDFs with Playwright — same pattern). Capture line cost = qty × price for a real PO total.
  6. Actually populate receiving: fill Qty Received on receipt (the field exists but is blank on every row today), driving partial-receive status on the PO header.
✓ Replaces Katana's PO function with something tailored to us — multi-vendor per part (which Katana can't do), our REQ numbering, our Teams alerts. Cancel Katana → net savings fund the build many times over.

Phase 3 — Self-maintaining inventory + predictive demand

Do later · ~1 week
Reuses: the BOM engine (already explodes orders), work-order-sync, the new PO system. New cost: $0.
Goal: Stop maintaining on-hand by hand, and see shortages before they block a build — the predictive layer that's the real reason MRPs exist.
  1. Auto-deduct on-hand. Two automations close the loop: PO/request marked Received → add qty to on-hand; Shopify order ships → BOM-explode it (engine already does this) → subtract consumed parts. This is the exact auto-deduction MRPs charge for — on the engine we already run.
  2. All-parts demand view. Generalize the wash-list explosion from "color parts only" to "every part across the whole open-order book." Publish as a hub view next to the wash list.
  3. Reorder suggestions. Combine on-hand + open demand + lead time into Katana's best feature: per part, a stockout date, suggested order qty, and order-by date. This is the "what to order and when" engine — without buying the engine.
  4. Self-tuning reorder points. Recompute reorder points monthly from rolling actual usage instead of a static seed — beating Katana, where safety stock is manual-entry-only.
✓ Completes full MRP feature parity for our use case — and on points 1 and 4 it's better than either vendor. On-hand stays live with no manual counting.

What we deliberately are NOT building

Saying no is half the value of this study. These are real MRP modules we're choosing to skip, with the reason — so nobody re-opens them later by accident:

  • Finite-capacity / Gantt scheduling — overkill for a 10-person batch shop. Batches + travelers already sequence the floor. (Even Katana doesn't really do true Gantt — it's priority-list auto-allocation.)
  • The MRP recalculation engine — the monolith that makes MRP hard to build and hard to trust. Phases 1 + 3 give us its two useful outputs (reorder + shortage) as simple, debuggable scripts. We don't need the black box.
  • BOM cost rollup / landed cost / WIP valuation — financial precision we get from QuickBooks at our volume. Defer indefinitely.
  • CRM / quotes / B2B portal — Shopify and draft orders already do this.
  • Shop-floor labor time tracking (kiosk) — the one "maybe." Only worth building if we decide we need labor cost per job. Park it; revisit if a margin question forces it.
  • Lot / serial traceability — both vendors gate it behind their priciest add-ons; we have no regulatory driver for it. Skip.

Bottom line

The plan: Phase 1 (~2–3 days) gives you inventory alerts — the thing you asked for. Phase 2 (~1–1.5 weeks) builds the PO system you suspected you wanted and lets us cancel Katana, saving ~$299+/mo. Phase 3 (~1 week) makes it self-maintaining and adds the predictive reorder layer that's the actual reason MRPs exist. Total recurring cost: $0. Total build: about three weeks, most of it reusing engines that already run. The result is a system that does the four things we need from an MRP — and does two of them better than MRPeasy or Katana, because it knows what Black Batch, (C) variants, and color batching are, and they never will.
